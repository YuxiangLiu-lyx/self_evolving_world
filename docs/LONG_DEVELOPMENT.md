# Long open development protocol

This opt-in `long-development-v1` policy builds on [fresh open development](OPEN_DEVELOPMENT.md).
It changes neither historical genesis nor archived generated capabilities. The
experiment is exploratory: no building, technology, leisure or cultural outcome is
required, and the joint changes are not a causal comparison.

conversation and submitted with `develop exN file.json`. No recursive model service or extra paid provider is used.

## Context and control queries

`long-context.ts` constructs fresh role-specific packets, without conversation
history. Full raw calls, events, checkpoints and source revisions remain archived.
Only owned/visible items, personal records and this run's implemented capabilities
are searchable. World queries can read only this registry, not other private memory.
Nested material properties remain hidden until real discovery.

A decision contains at most four read-only queries or one executable plan/review.
Two query batches are available per decision opportunity. Search, exact IDs, record
offsets and explicit JSON fragments provide bounded access to larger records. All
model responses are counted. Query results survive interruption and stay at the
same simulation round. They do not consume physical action time or create knowledge
rewards. Existing `consult` remains compatible, but ordinary control retrieval does
not require developing an inventory or ID-reading skill.

Current operation bindings, exact reserved items, paid elapsed/remaining work and
active extension state are never silently truncated. The relevant execution contract
is attached proactively. A packet that cannot fit the frozen guard pauses explicitly.
Other records use bounded pages with omission counts and retrieval identifiers.
The output schema is constant-size; `result_json` is decoded and the complete
current interface schema, plan, ownership and execution rules are still validated.
A rejected model response does not become an action. One bounded correction may
follow a parsed rejection; transport uncertainty or repeated rejection pauses the
world with the original journal intact.

Typical complete ordinary input targets 4000–8000 tokens; the complex-input
estimate ceiling is 14000. Estimates use pinned `js-tiktoken` 1.0.21, `o200k_base`:
the model mapping and server framing are approximate. Actual provider usage is
reported separately. Measurements include instructions, output schema, packet and
retrieval. Nested module counts overlap and must not be summed. UTF-8 byte-based
reservations are conservative cost ceilings, never described as token measurements.
See [before/after evidence](exec-plans/evidence/pr-31-long-open-development/context-before-after.json).

## Budget, stopping and repair

The entire new ordinary/world workload shares 10000000 input/output tokens,
including retrieval, failures and any probe. There is no reserved stage allocation:
roles and stages draw from one fungible pool. Attempt ceilings are 1800 ordinary,
100 world and 40 development handoffs. Output is capped at 3500 tokens per attempt.
An attempt reserves complete serialized request bytes plus the output limit and
4096 framing tokens before invocation. Known actual usage replaces its reservation;
unknown usage keeps the full reservation. Every attempt and elapsed time is journaled
before advancing the round barrier. Development, review and tool internal model
usage is not observable and remains **unknown**, not zero or included in this cap.

The offline forecast assumes 960 ordinary decisions, 20% retrieval overhead,
6000 input plus 700 output tokens per ordinary response, 60 world responses at
8000 combined tokens and 200000 allowance for unknown failures: 8398400 total.
This makes 1600 rounds plausible, not guaranteed. No technical probe is planned or
launched. There is no automatic budget increase or outcome-selected restart.

Stop/save at the observation target, exhausted lives, insufficient token/call budget
or an actual technical blocker. Ordinary checkpoints automatically continue.
Review/development waiting pauses simulation time. Technical repairs preserve the
failure and source boundary through the existing harness. Any incentive or environment
change after the first formal call requires a separately identified experiment.

## Source-bound mechanisms and representation limits

The retained development declarations distinguish new functionality, applicability
adapters and technical repairs. Root placement consumes real labor and retains a
real unverified specimen; it does not implement propagation or produce food.
Surface preparation moves finite cover into actual residues, and paid transfer
moves those residues to checked nearby extents. Later placement can depend on that
work. Source/person-bound adapter IDs are **not** independent physical inventions.

The loose-moss arrangement retains actual ground portions and measured contact;
its initial model supplies no assumed bedding bonus. The joining assessment first
recorded missing geometry. A later independent request authorized a versioned
piece model and actual paid loose wrapping/recovery. New geometry/continuity are
explicit modeling assumptions; paid observations expose bounded information from
that representation. They are not retrospective measurements or resource grants.
The [round82 boundary](exec-plans/evidence/pr-31-long-open-development/development-20.md)
records source reconciliation, implementation reuse, conservation, operation costs,
local heights and limitations. Calibrated force, load capacity and practical utility
remain unsupported. No request, mastery or completion label awards satisfaction.

Current-scope catalogue searches return compact functional entries. Exact IDs
retrieve full paginated applicability and execution contracts; ongoing operation
and escrow facts remain proactive. The retained round56 context pause and its
[repair](exec-plans/evidence/pr-31-long-open-development/development-16.md) expose
why broad searches must not repeat full schemas. Earlier raw requests remain
unaltered, and the complete-input ceiling was not raised. Raw requests, BPE module
estimates, actual usage and retained unknown-cost reservations are separate evidence.

## Stable retrieval pages and retained technical boundaries

The actual round157 pause exposed two defects: proactive and explicit retrieval
used different fragment widths, and broad searches returned unnecessarily large
record fragments. The repair uses stable600-code-unit JSON pages everywhere,
canonical observed-object wrappers and small search indexes. Page width is an
interface convention, not a token estimate. Exact IDs and explicit parts recover
the complete authorized record; out-of-range requests return a clear error.
Retained same-round query results are reprojected through the current authorized
reader, while original calls and responses remain immutable. Exact active work,
reserved identities, physical state, input ceiling and token policy are unchanged.
The [retained repair](exec-plans/evidence/pr-31-long-open-development/development-31.md)
records complete-request BPE estimates14489 before and12839 after; the next actual
provider input was11045 tokens. These are different measures, not interchangeable.

The two earlier explicit commentary/final-answer parsing repairs preserve the
original failed streams and known/unknown charges. Only the opt-in long-run reader
selects one completed final-answer message; ambiguous or unsupported responses
still fail. Interrupted transport is reconciled only after the experiment process and
worker are proved absent (`repair exN --abandoned-pid PID`); an unknown original invocation is never resent.
Development validation records all failed submissions as well as accepted source
boundaries. No repair silently resumes an exhausted token or call budget.
